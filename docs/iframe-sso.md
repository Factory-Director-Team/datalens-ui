# SSO для встраивания всего приложения DataLens в iframe

Эта интеграция включается явно и выполняет вход через **существующий общий локальный аккаунт DataLens**. Каждый вход из основного приложения создаёт отдельную полноценную сессию авторизации. Основное приложение и DataLens должны работать по HTTPS на соседних поддоменах одного сайта, например `https://app.example.com` и `https://bi.example.com`. Все родительские страницы в цепочке вложенных iframe также должны принадлежать этому сайту. Обычный вход в DataLens по логину и паролю и выход из него остаются доступны, в том числе при недоступности основного приложения.

## Настройка BFF

Задайте `AUTH_ENABLED=true`, `SSO_ENABLED=true` и перечисленные ниже переменные. Для каждого значения поддерживается вариант с суффиксом `_FILE`, позволяющий читать секрет из смонтированного файла. Включайте SSO после настройки эндпоинтов основного приложения, постоянного хранилища сессий и входящих маршрутов.

| Переменная                                                      | Назначение                                                                                                                    |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `SSO_HOST_ORIGIN`                                               | Точный HTTPS origin родительской страницы, без завершающего слеша                                                             |
| `SSO_BI_ORIGIN`                                                 | Точный HTTPS origin DataLens                                                                                                  |
| `SSO_TICKET_ISSUER`, `SSO_TICKET_AUDIENCE`                      | Точные значения издателя и получателя ticket                                                                                  |
| `SSO_TICKET_PUBLIC_KEY`                                         | Отдельный открытый RSA-ключ для проверки RS256 ticket основного приложения; использовать платформенный ключ DataLens нельзя   |
| `SSO_VERIFICATION_URL`                                          | Фиксированный эндпоинт проверки сессии основного приложения; используйте HTTPS либо закрытую сервисную сеть с аутентификацией |
| `SSO_SERVICE_TOKEN`                                             | Отдельный сервисный токен для запросов из BFF в основное приложение                                                           |
| `SSO_SHARED_LOGIN`, `SSO_SHARED_PASSWORD`, `SSO_SHARED_USER_ID` | Данные существующего локального аккаунта с полными правами и его закодированный идентификатор пользователя DataLens           |
| `SSO_REDIS_URL`                                                 | Отдельный основной узел Redis с постоянным хранением данных, общий для всех реплик BFF                                        |
| `SSO_MACHINE_TOKEN`, `SSO_MACHINE_USER_ID`                      | Необязательный отдельный токен машинного доступа длиной не менее 32 символов и идентификатор разрешённого машинного аккаунта  |

Существующие параметры `AUTH_ENDPOINT`, `AUTH_TOKEN_PUBLIC_KEY` и необязательный `AUTH_COOKIE_NAME` должны соответствовать используемому сервису auth; менять сам сервис не требуется. В конфигурации auth задайте `UI_APP_ENDPOINT`, равный origin DataLens, и `DISABLE_WILDCARD_COOKIE=true`. BFF устанавливает для выдаваемых браузеру cookies параметры Secure, HttpOnly, SameSite=Strict, Path=/ и ограничивает их текущим хостом. Отдельная cookie срока действия остаётся доступной для чтения и содержит только время истечения access token. Пароль общего аккаунта не передаётся в браузерный код.

Redis служит основным хранилищем сессий. **Вытеснение записей, допустимое для кэша, здесь недопустимо.** Используйте Redis 7 с постоянными томами, параметрами `appendonly yes`, `appendfsync always`, `maxmemory-policy noeviction`, ограниченным сетевым доступом и резервным копированием. Все операции чтения и записи должны обращаться к одному основному узлу. Не используйте отстающие реплики для чтения или переключение узлов, при котором могут теряться уже подтверждённые записи. Сведения о происхождении сессии неизменяемы и хранятся 31 день; абсолютный предел доступа по сессии составляет 30 дней. Сроки действия сессий и токенов auth должны укладываться в эти ограничения. Прежде чем увеличивать их, увеличьте срок хранения записей в реестре. Отсутствие записи означает отказ в доступе. Недоступность реестра блокирует и обычные сессии, тогда как недоступность основного приложения влияет только на SSO.

После включения реестра пользователям с существующими браузерными сессиями потребуется войти заново. Неизвестные cookies, выданные до внедрения, намеренно не считаются сессиями обычного входа. Предусмотрите повторный вход при развёртывании. При откате нельзя очищать реестр, пока выданные SSO-токены ещё позволяют авторизоваться: дождитесь завершения их действия или обеспечьте их недействительность, либо сохраняйте проверку реестра до этого момента.

## Контракт backend основного приложения

Реализуйте две операции в собственном слое аутентификации основного приложения. Его рабочий код находится за пределами этого репозитория. Тестовый backend в Docker показывает контракт и предназначен только для тестов.

1. **Выдача ticket**: `POST /bi/ticket` с существующей аутентификацией frontend основного приложения через `Authorization: Bearer …`. Тело запроса содержит `transaction_id` и `nonce`, полученные в запросе на вход от iframe. Определяйте `host_sid` по проверенной bearer-сессии и требуйте разрешение `datalens_access`. Отклоняйте отозванные и просроченные bearer-токены. Возвращайте `{ticket}` и заголовок `Cache-Control: no-store`.
2. **Проверка сессии**: `POST /bi/verify` с аутентификацией через `Authorization: Bearer <SSO_SERVICE_TOKEN>`. Тело запроса: `{host_sid}`. Возвращайте HTTP 200 с `{active: boolean, datalens_access: boolean}`, полученными из актуального основного источника состояния. Для неизвестной или отозванной сессии возвращайте false; HTTP 401 предназначен для неверного сервисного токена. После завершения выхода или отзыва доступа все последующие проверки должны видеть это изменение. Кэширование успешных проверок и чтение из отстающих реплик недопустимы. Сетевые ошибки, ответы вне диапазона 2xx и ответы неверного формата считаются временной недоступностью проверки. Тайм-аут BFF составляет две секунды.

Ticket подписывается алгоритмом RS256, содержит заголовок `typ: datalens-sso+jwt` и точные значения `iss`/`aud`. Обязательные поля: `host_sid`, `transaction_id`, `nonce`, уникальный `jti`, целочисленные `iat` и `exp`. Срок действия должен быть положительным и не превышать 60 секунд; `iat` не может находиться в будущем. Значения `transaction_id`, `nonce` и `jti` должны содержать от 16 до 128 символов: латинские буквы ASCII, цифры, подчёркивания или дефисы. BFF проверяет подпись и привязку к браузеру, атомарно погашает ticket и транзакцию для всех реплик, проверяет сессию основного приложения и затем вызывает обычный внутренний вход по логину и паролю. Если ticket не удалось погасить или на последующем шаге возникла ошибка, необходимо начать вход заново.

Bearer-токен пользователя основного приложения используется только его frontend и backend. Не передавайте его в DataLens и не храните в BI. Используйте разные секреты для подписи ticket, проверки сессий и общего аккаунта DataLens. Меняйте пароль общего аккаунта и соответствующий секрет BFF одновременно. При ротации ключа подписи ticket дождитесь истечения уже выданных ticket — не более 60 секунд, — обновите доверенный ключ на всех репликах и начните выдачу с новым ключом. Ротация сервисного токена также требует согласованного изменения обеих сторон.

## Подключение на родительской странице

Скопируйте `dist/public/sso-bridge.js` во frontend основного приложения или обеспечьте загрузку этого файла на его странице. Создайте экземпляр `DataLensSSO`, передав элемент iframe, точный `biOrigin`, асинхронную функцию `getTicket(challenge)`, возвращающую строку ticket, и необязательный обработчик `onStatus(code)`. Функция `getTicket` должна обращаться к операции выдачи ticket с bearer-аутентификацией основного приложения. При HTTP 401/403 отклоняйте промис с ошибкой, у которой `code` равен `HOST_DENIED`; при временной ошибке backend или сети используйте `VERIFICATION_UNAVAILABLE`. Для остальных ошибок библиотека сообщает `HANDOFF_FAILED`. Она проверяет точный origin сообщения, окно-отправитель, версию протокола и структуру запроса на вход, после чего отправляет форму методом POST на фиксированный callback DataLens с указанием этого iframe в качестве целевого окна.

Для входа в DataLens вызывайте `open()`. После явного выхода из BI iframe показывает сообщение «Вы вышли», а библиотека прекращает процесс входа. Привяжите кнопку «Открыть DataLens» в основном приложении к новому вызову `open()`. Не запускайте повторный вход автоматически из обработчика статуса. При выходе из основного приложения, смене аккаунта или сессии вызывайте `close()`: он скрывает старый iframe и отменяет незавершённый процесс входа. При размонтировании компонента вызывайте `destroy()`. Проверка BFF продолжает учитывать выход и отзыв доступа, даже если родительская страница пропустила уведомление интерфейса.

Библиотека не передаёт учётные данные основного приложения в iframe. Ticket передаются только в телах POST-запросов. Не добавляйте их в URL и не записывайте тела запросов входа в логи. Настройте CSP основного приложения так, чтобы разрешить загрузку скрипта интеграции, iframe DataLens и отправку формы на origin DataLens. Обратный прокси должен сохранять политику `frame-ancestors`, заданную BFF, и не добавлять конфликтующий заголовок `X-Frame-Options`. Сохраните отдельные правила встраивания для анонимных маршрутов Public link и Embed.

При обычной навигации с авторизацией внутри iframe отображается полный интерфейс приложения, включая его панели и меню. Явный режим `mode=embedded` и анонимный доступ сохраняют прежнее представление. Вкладки одного origin DataLens используют общую auth cookie: последний обычный вход или вход через SSO заменяет её и для остальных вкладок. Незавершённые процессы входа используют отдельные cookies транзакций. В одном профиле браузера нет независимых наборов cookies для обычного входа и SSO.

## Защищённые маршруты и машинный доступ

Все HTML-страницы и запросы API, данных и экспорта, требующие авторизации, проходят проверку политики SSO. Она также применяется к автоматическому обновлению токенов при открытии HTML-страницы и прямому обновлению через auth gateway. Запросы сессий обычного входа используют тот же локальный реестр, но не обращаются к основному приложению. Выход из текущей сессии доступен без проверки основного приложения и отзывает только переданный идентификатор сессии DataLens. Отказ основного приложения отзывает привязку сессии; временная недоступность проверки блокирует запрос, сохраняя привязку действующей.

Не открывайте браузерам прямой доступ к auth, United Storage, data/control API и отдельному сервису `ui-api`. При включённом SSO внутренние маршруты переноса объектов на публичном UI также требуют проверки браузерной сессии. Межсервисные запросы переноса направляйте на отдельный закрытый сервис `ui-api`. Тестовый обратный прокси полностью блокирует `/api/internal/`. Перед развёртыванием проверьте фактически доступные маршруты рабочего прокси.

Для существующих запросов MCP задайте в MCP переменную `DATALENS_BFF_MACHINE_TOKEN`, совпадающую с `SSO_MACHINE_TOKEN`, а в `SSO_MACHINE_USER_ID` укажите идентификатор аккаунта, от имени которого MCP подписывает токены. MCP передаёт дополнительный секрет только своему эндпоинту BFF вместе с существующей подписанной auth cookie. BFF проверяет и платформенную подпись с аккаунтом, и отдельный сервисный токен. Для запросов с браузерными заголовками Origin/Fetch Metadata и для HTML-маршрутов это исключение недоступно. Неизвестного идентификатора сессии или произвольного значения заголовка недостаточно. Защищайте машинный секрет и канал его передачи так же, как другие сервисные учётные данные. Обычные браузерные сессии его не получают.

Отзыв доступа в основном приложении прекращает SSO-доступ при следующем защищённом запросе, начатом после завершения отзыва. Он не может удалить уже отображённые данные или отменить ранее разрешённые действия. Пользователь, знающий действующий пароль локального аккаунта DataLens, по-прежнему может войти напрямую после отзыва доступа в основном приложении — это согласованная политика. В аудите DataLens действия остаются связанными с общим аккаунтом.

## Приёмочные проверки в Docker

Из репозитория UI выполните `bash tests/sso/run.sh`. Чтобы ограничить проверки входа одним браузером, выполните `bash tests/sso/run.sh --project=chromium handoff.test.ts`.

Изолированный Compose-проект собирает локальные исходники UI и US, использует неизменённый auth версии 0.34.0, запускает две реплики BFF и Redis с постоянным хранением. В стенд входят тестовый backend основного приложения, тестовые учётные данные и сертификаты, HTTPS-прокси для поддоменов одного сайта и Playwright с Chromium, Firefox и WebKit. Этап проверки жизненного цикла реестра всегда выполняется во всех трёх браузерах. Он сохраняет состояние браузеров между реальными перезапусками BFF и Redis, остановкой и восстановлением Redis, а также потерей временного тестового реестра. Отдельное тестовое ограничение памяти Redis проверяет отказ сохранения привязки после реального входа в auth. Проверки опираются на результаты HTTP-запросов и поведение браузера без чтения внутренних записей реестра. Рабочее основное приложение и его учётные данные не требуются; порты внутренних сервисов наружу не публикуются. Отчёты сохраняются в `tests/artifacts/sso`. При завершении скрипт удаляет только временные контейнеры и тома этого тестового проекта.

Управляющие маршруты тестового backend и тестовые ключи подписи существуют только внутри стенда. Не развёртывайте этот backend вместо рабочего основного приложения. Перед внедрением проверьте соблюдение контракта отзыва сессий в реальном основном приложении и отдельно выполните проверки в настоящем Safari: успешный прогон WebKit в Docker не подтверждает работу Safari. Фиксируйте фактические результаты тестов, включая ошибки инфраструктуры. Обнаружение тестов и проверка конфигурации Compose не считаются успешным браузерным прогоном.
